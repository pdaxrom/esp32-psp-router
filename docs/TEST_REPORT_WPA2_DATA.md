# WPA2: передача данных и ARP, 8 ноября 2026

Рабочая WPA1/NAT/proxy версия: commit `350a84a`. WPA2 handshake отдельно
подтверждён после полного перезапуска ARK-5. Это не подтверждало доступность HTTP.

## Наблюдения на 2.1.2

При таймауте локальной страницы ESP видела станцию 00:23:4e:17:88:02,
DHCP lookup возвращал 192.168.50.2, ARP lookup — 0.0.0.0. Новых принятых
TCP-соединений не было. Полный перезапуск PSP не устранил отказ.

Первый внешний захват `dist/psp-wpa2-data.pcap` совпал с переподключением WLAN
PSP и успешными HTTP-запросами. M2 на Mac был повреждён (bad FCS), поэтому
первый файл не позволил расшифровать эту сессию. После завершения захвата
пользователь снова сообщил об отказе страницы.

Второй захват `dist/psp-wpa2-compare.pcap` содержит полный M1–M4 и корректный
MIC M2. Сессионные ключи вычислялись только в памяти анализатора; в текстовый
отчёт не выводились. Последующая AES-CCM аутентификация пакетов успешна в обе
стороны. Краткий протокол — `dist/psp-wpa2-compare-analysis.txt`.

В закреплённой IDF `dhcps_response_ip_set()` временно создаёт статическую
ARP-запись для unicast DHCP. `etharp_add_static_entry()` также отправляет
накопленные пакеты. После DHCP отправки IDF удаляет эту запись.
SYN-ACK перед OFFER показывает, что ESP уже обработала предыдущий SYN,
но ответ ждал разрешения адреса. После ARP-объявления PSP HTTP работает.
При последующем наблюдении запись PSP снова исчезла из ARP, станция оставалась
подключённой. Это объясняет отказ до HTTP-прокси; причина отсутствия ответов
PSP на broadcast ARP, включая возможную особенность GTK ARK, пока не доказана.

Пользователь подтвердил, что после окончания второго захвата страница всё ещё
открывалась. Необходимость постоянно работающего monitor mode не подтверждена;
его включение и переподключение WLAN в первом опыте происходили одновременно.

## Исправление 2.1.3

WPA2/router хранит до четырёх привязок IP/MAC из локальной DHCP-таблицы для
текущего списка Wi-Fi станций. Они обновляются примерно раз в 300 мс, в контексте
TCP/IP. Не допускаются адрес ESP, broadcast, адреса другой подсети/интерфейса.
Отслеживаемые привязки удаляются при уходе станции, смене аренды и LAN-подсети;
чужие записи ARP не удаляются. USB WAN и отдельная WPA1-сборка не затрагиваются.

Все шесть сборок из основного отчёта и проверки ELF/config прошли. В WPA1
ARP-код отсутствует. WPA2/AES, EAPOL, прокси и проверка TLS не меняются.
Образ прошит: esptool проверил хэши всех трёх компонентов и завершился кодом 0.
Приложение ответило по USB, WAN 192.168.2.6/24, LAN 192.168.50.1/24, часы готовы.
В первом подключении PSP на 2.1.3 одновременно видны DHCP/ARP 192.168.50.2,
приняты два TCP/HTTP запроса, ошибок разбора нет. Радиозахват не работает.
Протокол дальнейшего наблюдения — `dist/router-213-arp-watch.jsonl`.
Пользователь подтвердил локальную страницу и zond.am через proxy на PSP без
радиозахвата. Повторные ассоциации и запросы видны в счётчиках ESP, привязка
DHCP/ARP присутствует. Полный USB-host live-прогон прошёл, включая сертификаты,
переписывание ссылок, параллельность и три загрузки 64 КиБ.
В 355 валидных снимках подключённой PSP ARP-привязка ни разу не пропала;
одна ассоциация наблюдалась 362,3 с. Недоступные ответы во время проверки
параллельности исключались из анализа; это выборочные наблюдения, не полный
пакетный протокол.
Длительный простой и возврат к странице, нагрузка через Wi-Fi и стресс
переподключений отдельно не приняты; это не часть подтверждения базовой работы.
